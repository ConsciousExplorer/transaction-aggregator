KeysetPage or CursorPage?

    
Keep KeysetPage. It holds rows, and the cursor is made from them one layer up.

    

      
Keyset is the technique: seek past the last row's sort key instead of counting rows. A cursor is what the client holds: a position it sends back. The code already uses each word for its own layer:

Why not CursorPage

      
It would say the object carries cursors when it carries rows. The route turns nextFrom into a cursor with buildPageCursor, and that step is where the word should change.

      
In Postgres, a cursor is DECLARE … CURSOR: a server-side position held open between fetches. Keyset paging holds nothing between requests, and that is its whole point. Keeping "keyset" on the database side avoids an interviewer asking whether a cursor stays open between page requests.

      
buildKeysetPage(fetched, limit, cursorDirection, hasCursor) takes cursor words as inputs. That is correct: they are facts about the request, not about the page.
