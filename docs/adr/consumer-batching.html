Consumer Flush Simulator

A playable model of the consumer's batching loop. Records come off Kafka in fetches, wait in the stream's buffer, and the for await loop moves them one at a time into a batch. A batch is flushed when it holds 100 records, or 2 s after its first record arrived. A flush inserts the batch in one Postgres transaction, then commits the Kafka offset.       One loop, two ways to flush

      The whole consumer is one for await loop over the message stream. Each pass adds one record to the batch. The first record starts a linger timer. The hundredth record makes the loop await a size flush.

      // apps/consumer/src/integrations/events/kafka.ts:390-410
for await (const message of messageStream) {
	state.messages.push(message);

	if (state.messages.length === 1) {
		state.lingerTimer = setTimeout(() => {
			flushBatch(state, "linger").catch((error: unknown) => {
				messageStream.destroy(
					error instanceof Error ? error : new Error(String(error))
				);
			});
		}, options.lingerMs);
	}

	if (state.messages.length >= options.batchSize) {
		await flushBatch(state, "size");
	}
}

await flushBatch(state, "stream_end");
      • The size flush is awaited, so the loop takes nothing more from the stream until the insert and the commit are done. That wait is the consumer's only backpressure. Nothing calls pause().
      • The linger flush runs from a timer callback, which can't be awaited. The loop keeps filling the next batch while it runs.
      • Both go through flushBatch, which chains every flush onto one promise, so two flushes never run at the same time.
      // kafka.ts:353-362, comments trimmed
function flushBatch(state: BatchState, trigger: FlushTrigger) {
	const flushed = state.inFlight.then(() => drainBatch(state, trigger));
	state.inFlight = flushed;
	return flushed;
}

      Which trigger fires

      A batch reaches 100 records within 2 s only when records arrive faster than 50 a second. A backlog always does, so catch-up is all size flushes. The live stream is slower, so it is all linger flushes.

      What one flush does

      1. Waits for the flush before it to settle (state.inFlight).
      2. Clears the linger timer and swaps state.messages for a new array. The loop can start the next batch straight away.
      3. Sorts the batch into valid records, poison records (failed to deserialise) and tombstones.
      4. Categorises the valid records and inserts them in one Postgres transaction. ON CONFLICT DO NOTHING skips any it already stored.
      5. Sends poison records to the dead-letter topic with their raw bytes and headers.
      6. Commits the highest offset of each partition. The group's offset moves only now, after the data is stored.

      Measured here: 59 ms per flush on average (p50 41 ms, p95 198 ms), 49 ms of it the insert, for full batches of 100. One consumer works through about 1,700 records a second while catching up.

      Why memory stays bounded

      When a fetch comes back, the stream deserialises and pushes every record in it, whatever push() returns. The return value only decides whether the next fetch is scheduled. Once the buffer holds 1,024 records or more, fetching stops until the loop has taken it back under 1,024; Node then calls _read(), which fetches again.

      So the most the stream can hold is just under 1,024 records plus one whole fetch. KAFKA_FETCH_MAX_BYTES caps a fetch at 1 MiB. The client's 50 MB default held about 144,000 card records, about 360 bytes each, and the consumer was OOM-killed working through a backlog. At 1 MiB a fetch holds about 2,900.

      1,023 in the buffer + 2,900 from one fetch + 100 in the batch + 100 in the flush ≈ 4,100 records at most

      Watch the buffer in the Backlog load: it jumps by a fetch, falls by 100 per flush, and fetches again once it drops under the 1,024 mark.

      When a flush fails

      What went wrongWhat the flush doesOffset
      Poison record: the bytes don't deserialiseInserts the rest, sends the poison record to the DLQCommitted
      Bad row: Postgres rejects it with SQLSTATE class 22 (data) or 23 (constraint)Rolls the batch back, inserts the records one at a time, sends the bad one to the DLQCommitted
      Anything else: Postgres down, connection lost, any other SQLSTATEThrows a RetryableError. The flush rejects, and so does every flush queued behind it, without inserting or committing.Not committed

      A rejected flush ends the process. A size flush rejects the loop's await. A linger flush destroys the stream from its .catch. Either way the loop throws, app.ts closes the consumer so it leaves the group, and the process exits with code 1. Docker restarts it, it rejoins at the committed offset, and it reads the uncommitted records again. While Postgres is still down the boot check fails, so the container restarts over and over until Postgres is back.

      A Kafka commit that fails after a successful insert is only logged. The next batch's commit moves the offset past it. If the process dies before that, the records are read again and ON CONFLICT DO NOTHING skips them. Delivery is at least once, and the table stores each record once.

      Node details that shape it

      • A fetch response is handled in one callback: every record is deserialised and pushed before anything else runs. The next fetch is then scheduled with process.nextTick, which gives heartbeats and commits a turn between fetches.
      • The broker holds a fetch that finds no records for up to KAFKA_MAX_WAIT_TIME_MS (1 s) and answers as soon as one arrives. At 25 records a second that means fetches of about one record each.
      • autocommit is off. Offsets move only through commitBatch, after the batch is stored.
      • Each batch is its own trace, consume.batch, with links to the producers' traces rather than a parent.
