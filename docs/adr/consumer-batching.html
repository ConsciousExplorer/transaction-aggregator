Consumer Flush Simulator

A playable model of the consumer's batching loop. Records come off Kafka in fetches, wait in the stream's buffer, and the for await loop moves them one at a time into a batch. A batch is flushed when it holds 1,000 records, or when the stream has nothing more buffered, which means the fetch is used up. The broker does the waiting: it answers a fetch once 32 KiB are ready or 2 s have passed. A flush inserts the batch with one statement, then commits the Kafka offset.       One loop, one awaited flush

      The whole consumer is one for await loop over the message stream. Each pass adds one record to the batch, then asks two things: is the batch full, and does the stream still hold anything? If neither, it reads on. Otherwise it awaits a flush, and reads nothing more until the flush and its commit are done.

      // apps/consumer/src/integrations/events/kafka.ts, startBatchConsumer
let batch: KafkaMessage[] = [];
for await (const message of messageStream) {
	batch.push(message);

	const isFull = batch.length >= options.batchSize;
	if (!isFull && messageStream.readableLength > 0) continue;

	await flushBatch(batch, onBatch, topic, isFull ? "size" : "fetch");
	batch = [];
}
      • Every flush is awaited, so one runs at a time and the loop takes nothing from the stream while it runs. That wait is the consumer's only backpressure. Nothing calls pause().
      • readableLength is how many records the stream still holds. The client pushes a whole fetch before the loop sees any of it, so right after a record is taken, that number is how much of the fetch is left. Zero means the fetch is used up, and the batch goes now rather than waiting for the next fetch.
      • There is no timer in the consumer. Holding records back until enough have arrived is the broker's job: it answers a fetch once 32 KiB are ready or 2 s have passed, whichever comes first.

      Which trigger fires

      A fetch of 2,900 records is flushed as two batches of 1,000 and one of 900. A fetch of 50 is flushed as one batch of 50. So a backlog is mostly size flushes, and the live stream is all fetch flushes.

      TriggerFires whenDoes the loop wait?When you see it
      sizethe 100th record joins the batchYes, until the insert and commit finishA backlog: every fetch holds thousands
      fetchthe record just taken was the last one the stream heldYes, the same waitThe live stream: a fetch holds what gathered in up to 2 s, far fewer than 1,000

      The stream ends only when shutdown closes the consumer. Whatever it still held was never committed, so the restart reads those records again.

      How the broker gathers a batch

      A fetch request carries two limits besides its size cap. fetch.min.bytes (KAFKA_FETCH_MIN_BYTES, 32 KiB) is how much the broker gathers before it answers, and fetch.max.wait.ms (KAFKA_MAX_WAIT_TIME_MS, 2 s) is how long it will hold the request to get there. A card record is about 360 bytes, so 32 KiB is about 90 records.

      • A backlog is answered at once with a full 1 MiB, about 2,900 records.
      • At 150 records a second, 32 KiB gather in about 0.6 s, and the fetch comes back then with about 90 records.
      • At 25 records a second, 2 s pass first, and the fetch comes back with about 50.
      • At 2 records a second, the fetch comes back after 2 s with a handful.

      So the longest a record waits before it is read is 2 s, and the consumer needs no timer to promise that. The next fetch is already in flight while the loop works through the last one, because the stream fetches again as soon as its buffer has room.

      What one flush does

      1. Takes the batch the loop handed it. The loop starts a fresh array once the flush resolves.
      2. Sorts the batch into valid records, poison records (failed to deserialise) and tombstones.
      3. Normalises, validates and categorises each valid record on its own, before any SQL runs. A record that can't become a row is set aside for the dead-letter topic, and the rest of the batch is unaffected.
      4. Inserts the rows with one statement. ON CONFLICT DO NOTHING skips any it already stored.
      5. Sends the poison records and the records set aside to the dead-letter topic in one produce call, with their raw bytes and headers.
      6. Commits the highest offset of each partition. The group's offset moves only now, after the data is stored.

      Measured on 2026-10-31 against a 14-million-row table: a full batch of 1,000 takes 442 ms per flush at the median (p95 1.1 s), 434 ms of it the insert, and one consumer stores about 2,500 records a second while catching up, against 2,200 with batches of 100 on the same table. Most of the insert is Postgres reading index pages: three indexes, and dates spread over 18 months, so every row touches pages across every partition. On the live stream every row lands in the current month's partition, whose pages stay in memory: there a batch of about 300 inserts in 20 ms and one consumer keeps up with 5,800 records a second.

      Why memory stays bounded

      When a fetch comes back, the stream deserialises and pushes every record in it, whatever push() returns. The return value only decides whether the next fetch is scheduled. Once the buffer holds 1,024 records or more, fetching stops until the loop has taken it back under 1,024; Node then calls _read(), which fetches again.

      So the most the stream can hold is just under 1,024 records plus one whole fetch. KAFKA_FETCH_MAX_BYTES caps a fetch at 1 MiB. The client's 50 MB default held about 144,000 card records, about 360 bytes each, and the consumer was OOM-killed working through a backlog. At 1 MiB a fetch holds about 2,900.

      1,023 in the buffer + 2,900 from one fetch + 1,000 in the flush ≈ 4,900 records at most

      Watch the buffer in the Backlog load: it jumps by a fetch, falls by 1,000 per flush (or by what was left of the fetch), and fetches again once it drops under the 1,024 mark.

      When a flush fails

      What went wrongWhat the flush doesOffset
      Poison record: the bytes don't deserialiseInserts the rest, sends the poison record to the DLQCommitted
      Invalid record: it decodes, but can't become a row (a bad currency, a field too long, a date more than a day ahead)Set aside before the insert, so the rest still go in one statement; sent to the DLQ with the poison recordsCommitted
      Bad row: Postgres rejects it with SQLSTATE class 22 (data) or 23 (constraint)The one statement fails as a whole. The records are inserted one at a time, and the bad one is sent to the DLQCommitted
      Anything else: Postgres down, connection lost, any other SQLSTATEThrows a RetryableError. The flush rejects, and nothing is committed.Not committed

      A rejected flush ends the process. The loop's await rejects, so the loop throws, app.ts closes the consumer so it leaves the group, and the process exits with code 1. Docker restarts it, it rejoins at the committed offset, and it reads the uncommitted records again. While Postgres is still down the boot check fails, so the container restarts over and over until Postgres is back.

      A Kafka commit that fails after a successful insert ends the process the same way. The rows are stored, so the restart reads those records again and ON CONFLICT DO NOTHING skips them. Delivery is at least once, and the table stores each record once.

      Node details that shape it

      • A fetch response is handled in one callback: every record is deserialised and pushed before anything else runs. The next fetch is then scheduled with process.nextTick, which gives heartbeats and commits a turn between fetches.
      • Node's for await over a Readable takes one record per pass with read() and keeps no read-ahead of its own, so readableLength is exactly what the stream still holds.
      • autocommit is off. Offsets move only through commitBatch, after the batch is stored.
      • Each batch is its own trace, consume.batch, with links to the producers' traces rather than a parent.
