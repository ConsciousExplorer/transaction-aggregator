CI Pipelines

Six GitHub Actions workflows guard the repo: one per app (api, consumer, portal, producers) and one for each contract the apps share with the outside (the API's OpenAPI document and the Avro schemas). Each workflow first works out whether anything it cares about changed, and skips its checks if nothing did. A pull request into main gets three more checks: the app's version went up, the API still serves the clients it served before, and the schemas can still read the records already on Kafka.

What starts a run

  • Events. Every workflow runs on a pull request into main. Five also run on a push to any branch; schemas runs on a push to main only.
  • The changes job always runs. It uses dorny/paths-filter to decide whether the workflow's files changed. On a push it compares with the commit before the push; on a pull request it reads the pull request's changed files through the GitHub API, which is why each workflow asks for pull-requests: read.
  • Skipped is passed. When nothing relevant changed, the other jobs are skipped by their if:, and GitHub counts a skipped job as passed. That is why the changes job exists rather than a path filter on the workflow's trigger: with a trigger filter the workflow would never start, and a required check on main would wait for it forever.
  • One run per branch. Each workflow sets concurrency per branch with cancel-in-progress, so a new push cancels the run still going for the one before it.
  • Pinned tools. Node 24.20.0 for the Node apps, the Python in apps/producers/.python-version through uv, and the oasdiff release binary checked against a SHA-256.

When the version must go up

Once per pull request into main, not once per commit: the check compares the branch's version with main's, so one bump covers every commit in the pull request. It only asks for a higher number. Whether that is a patch, minor or major bump is your call; a breaking API change is blocked by the contract check whatever the version says.

What breaks the API contract

The rule is the client's: anything a client built against main's contract does today must keep working. So responses may gain, and requests may loosen. A response may not lose or change a field, and a request may not demand more. Each row below was tried on the committed openapi.json with oasdiff 1.32.1, the version CI pins.

Adding a response enum value fails because a client may switch on the values it knows, and would meet one it doesn't. To change a field, add the new one beside the old one; removing the old one later is a breaking change, and this check stops it.

The one gap: filters that take one value or a list

transactionType and creditDebitIndicator accept one value or an array, so their schema is anyOf: [enum, array of enum]. oasdiff 1.32.1 doesn't compare enums inside an anyOf: removing a value there reports nothing, yet a client still sending it now gets a 400. Removing loan from transactionType was this kind of change. Until the check covers it, a reviewer has to catch it.

What breaks an Avro schema

The schemas face the other way. The registry is set to BACKWARD: a new version must be able to read the records written with the version it replaces, because those records are still on Kafka. The registry refuses a version that can't, so CI runs the same check first, without a registry, using avsc's resolver. It checks each schemas/<name>.avsc against the same file on main, and each schemas/v<N>/<name>.avsc against the top-level schema it evolves from. Each row below was tried on schemas/card.avsc with that resolver.

ChangeTried asResultWhy

So removing a field breaks the API contract but not an Avro schema, and adding one is the reverse: free in an API response, but an Avro field needs a default. Removing a field the consumer reads still gets caught: the consumer workflow regenerates its types from schemas/ and fails if the committed ones differ, and the type-check then fails wherever the code reads the field.
